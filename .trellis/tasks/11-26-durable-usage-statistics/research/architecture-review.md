## Accepted/frozen contract areas

1. **Lifetime channel/model readers use dedicated rollups.** `usage_channels` and `usage_channel_models` avoid grouping the event fact history or summing hourly history for all-time channel-card reads. Empty-model contribution is intentionally included in the channel aggregate but excluded from the model-detail summed total, matching current source behavior. `last_used_at` is max of the exact stored event second.
2. **Prepare and projection are separate, durable phases.** A prepared fact retains its full immutable numeric payload. Apply uses one primary transaction for hourly + channel lifetime + channel/model lifetime measures and the applied marker. A worker retries only statistics; it never replays money. Pending-aware reads must use one statement snapshot or fail not-ready, and never return a truncated total.
3. **Cross-dialect first-claim protocol is concrete in p5's proposal.** Insert-do-nothing followed by an authoritative locked read, full identity/payload comparison, then projection only for the persisted owner avoids preselect/RowsAffected/LastInsertID ownership inference. SQLite writer reservation, real relational locks, deterministic bucket order, checked Go-side int64 adds and same-tx marker are specified. These are proposed mechanics, not verified database behavior; hosted matrix remains mandatory.
4. **Identity and historical lineages are separated.** Event key is not request ID or mutable quota; task sequence is a winning operation identity. Live logs carry the canonical admin-only event key. Frozen `quota_data` remains the dashboard baseline, post-fence live facts feed new dashboard hours, and historical log import feeds exact log/channel rollups rather than being blindly added to the baseline.
5. **The synchronous guarantee is explicitly limited.** Statistics durability starts only after finalized numeric Prepare succeeds. Existing settlement/response behavior proceeds once on preparation failure; no funding/refund replay is allowed. A pre-prepare crash or primary outage with logging/export disabled can leave unrecoverable quantities. The once-per-writer epoch is only coarse loss detection, not event recovery.
6. **The epoch gate is conditional, not currently proven.** p5 defines a per-writer open/clean-sealed epoch. Safe sealing requires registration before any source work, comprehensive admission and detached-finalizer tracking, sticky unresolved state, admissions fenced before a closed-world drain, and a new open epoch before resume. Restart, heartbeat expiry and empty queues cannot seal. Current source lifecycle implementation has not been reviewed/verified; until it is, coverage/deletion readiness remains false. The design does not certify active time prefixes or unattended rolling 24-hour deletion.
7. **No-budget and conditional async outcomes are not misrepresented as finance-atomic.** Task candidate/operation identity is attached to the winning CAS/insert; source owner alone confirms its report outcome. Generic settlement errors stay unknown unless a no-report result is proven. No automatic promotion, re-debit, or inference from task quota/status. A crash between a nontransactional money operation and confirmation can remain unknown and block deletion; the design does not promise recovery without durable same-occurrence evidence.

## Narrow query/index decisions

### Pending-tail indexes

p5's existing `ix_usage_event_time(source_state, kind, occurred_at, id)` and `ix_usage_event_self(user_id, source_state, kind, occurred_at, id)` support exact-range fact queries, but do not bound a ready/unapplied tail by `applied_version=0`: that equality column must precede the time range. The drain index lacks kind/time, so it cannot substitute.

Smallest concrete schema/query clause:

- Preserve the existing time/self indexes for queries over all matching facts.
- Add one dedicated global tail index `(source_state, applied_version, kind, occurred_at, id)` for ready, unapplied, kind/time-bounded projections.
- Add the user-leading variant `(user_id, source_state, applied_version, kind, occurred_at, id)` only if a user-scoped projection tail is actually queried. Keep the already proposed channel-tail index for channel-keyed tails. Do not widen every event index or force exact-fact queries through `applied_version`.
- Query with equality predicates for state/version/kind before the range, and keep the 1,001-row sentinel/error contract. Hosted query-plan and bounded-tail behavior remains required; index presence alone is not proof.
- Keep `ix_usage_event_drain(source_state, applied_version, next_attempt_at, id)` for delayed statistics-only retry selection (`ready`, unapplied, due); retries do not alter source readiness or clear source-unknown coverage. The time-range tail indexes serve reads and are not substitutes for this drain index.

This is the smallest access path that prevents a pending-tail request from walking applied history. Include its incremental bytes in the capacity gate below.

### Exact text comparisons and digest filters

Native exact request/upstream-request SQL filters must not exclude rows with a byte-hash prefilter unless byte-exact equivalence is proven for each supported dialect/collation and stored representation. Case-insensitive or trailing-space-insensitive equality can match different bytes; full-text verification after an excluding hash cannot recover a false negative. Keep the existing native-compatible full-text equality predicate otherwise, and preserve literal-substring and wildcard behavior. SQLite/MySQL/PostgreSQL parity is a reader-cutover gate. The digest columns may not become an exclusion predicate by default.

## Practical cleanup readiness: certify rows, not an entire live epoch

### Decision

**Yes: allow deletion of an individually persisted source row once its exact numeric occurrence has been durably imported/linked and verified in primary storage. Do not require every currently active upgraded writer epoch to be sealed before deleting that already represented row.** Keep row-level deletion readiness separate from whole-history/statistics completeness. This is a cleanup authorization for proven retained rows, not a claim that no usage was lost before Prepare.

### Minimum per-row / source-range evidence

1. For a new live keyed log row, resolve its stable `usage_event_key` to the primary fact. Compare the full source binding and immutable finalized numeric/filter payload, not request ID or digest alone. The occurrence must be source-confirmed `ready` and `applied_version=1` for all applicable projections. If the fact is absent, pending/unknown, conflicting, or not fully applied, retain the row. A retry may recover only the same key/payload; it must not create a replacement identity or replay finance.
2. For a relational legacy log, use stable source namespace plus the actual persisted log row ID as the canonical imported identity. The immutable source manifest/partition must be verified, the checkpoint must commit with every imported row obligation, and that exact row's event must be present, payload-verified and applied before deletion. Sparse IDs or a high-water mark alone do not prove row coverage.
3. ClickHouse `id=0` and display ordinals are not row identities. Its legacy deletion unit must be a frozen, verified source time-range/manifest containing the complete physical-row count, tuple multiplicities/ordinals, and imported payload totals/digest. The existing `DeleteOldLogBatch` ClickHouse path issues one synchronous delete for the entire `< cutoff` predicate; it may run only when **every** physical row that predicate can remove is covered, including keyed post-fence rows. A count-only check is insufficient. Since this mutation can also catch an append arriving after a pre-scan, require a narrow source-range quiescence fence/no-late-old-timestamp guarantee for the actual mutation window (only callbacks capable of publishing into that target range must drain or remain fenced). An unrelated open epoch with no such pending range work need not block. If exact affected-set and append fencing cannot be demonstrated for the existing broad predicate, keep ClickHouse cleanup paused or change the application path to a bounded manifest-aligned mutation; do not call it per-row gated.
4. Keep the authoritative guard below controllers: check at the system-task path and enforce again in `model.DeleteOldLogBatch`. A relational batch may delete only exact candidate IDs whose row evidence passed; fail closed on an unresolved candidate. For ClickHouse, enforce the complete manifest and narrow no-late-write fence for the full mutation range. A separate LOG_DB/primary DB is not a distributed transaction, so rely on immutable source rows/manifests and durable primary facts; re-read/revalidate exact candidates immediately before destructive work. Native ClickHouse TTL remains an independent operator-controlled deletion path and must be paused/protected until its affected source range is verified.
5. Fence and drain **legacy/unupgraded writers** before freezing the historical manifest; otherwise they can append unidentified rows behind its checkpoint. This one-time source-fence requirement is distinct from requiring every current, upgraded writer's OPEN epoch to close before each cleanup batch. Current writers may continue: any row they publish is removable only when its own keyed durable fact meets clause 1.

An unrelated current `OPEN` epoch, by itself, does not revoke proof already attached to a particular imported/applied relational row and should not make old logs permanently undeletable. For a ClickHouse predicate deletion, only an epoch with an unjoined or unresolved finalizer that could still publish into that exact time-range is relevant to the narrow mutation fence; whole-epoch sealing is not required. Conversely, a row/range pass must not clear, seal, or rewrite that epoch's global status. If an unresolved occurrence could be the source of a candidate log row, that row fails its own evidence check and stays retained.

### What the row gate cannot prove

A crash or primary outage before finalized Prepare may lose a quantity even while billing/response proceeds. If no durable fact or surviving keyed log/source payload exists, there is no row to import and no quantity to reconstruct. An OPEN/unknown epoch is conservative evidence of this possible gap, not a list of missing values. Deleting every individually verified retained row therefore does **not** establish global exactness, prove active-time prefixes, or authorize an unattended rolling-24-hour claim. Keep whole-history/source coverage partial or unknown while relevant writers/roles remain unsealed/unknown, source manifests are incomplete, or a loss gap is unresolved. Never fill it with zero, account counters, current prices or a finance replay.

This separation gives operators a useful monotonic result: verified rows can become disposable while an unrelated live epoch remains open, but the global completeness/deletion-ready signal stays false wherever the epoch/gap affects the claimed coverage. Displaying/recording row cleanup readiness and global statistics coverage as different states avoids turning cleanup progress into a false completeness assertion.

## 20 GB capacity gate

The supplied production observations (not queried by p4) report about 1.68 million usage logs, 2.7 GB of log rows and a full 20 GB volume. p5's maximum bounded text payload is roughly 27 KiB/event; multiplied by 1.68 million, that is about **46 GB of text at the declared maxima alone**, before row headers, numeric columns, secondary indexes, hourly/lifetime projections, WAL or migration overhead. That is a worst-bound illustration, not an estimate of typical rows, but it proves the declared per-field limits do not themselves demonstrate that the new store fits the reported volume.

Smallest safe capacity decision before backfill/activation:

- Measure actual row plus index bytes and hourly/lifetime cardinality on a representative, authorized non-production copy/sample; include the new pending-tail indexes. Measure peak WAL/index-build/compaction needs while source logs remain available for verification and include live growth through the chosen retention period. Do not infer statistics size or savings from the current 2.7 GB log size, request-content compression, PostgreSQL TOAST, or ClickHouse compression.
- Require available peak headroom to cover that measured incremental peak plus an explicit operations reserve. If it does not fit, enlarge/move the primary DB volume or otherwise provision sufficient primary capacity **before** backfill; do not delete the only source first to make room for an unverified target.
- PostgreSQL log deletion makes pages reusable internally but does not return OS space without a separately authorized `VACUUM FULL`/`pg_repack`-style operation, which itself needs workspace. Therefore do not promise immediate physical reclamation or treat the 20 GB disk pressure as solved by deleting rows. No p4 production query, cleanup, compaction, or setting change was performed.

This capacity gate remains unverified until the owner supplies a representative footprint and peak-space result; no arbitrary storage ratio or disk-saving claim is approved.

## Final review disposition and root clauses

This bounded source/architecture review is **READY for root to converge the implementation contract**; it does not approve production rollout, database compatibility, cleanup, or whole-history exactness. No further inventory or broad source redesign is requested. Root-owned PRD/design/implementation artifacts should carry these concise decisions:

1. **Per-row cleanup is distinct from global coverage.** A relational retained row is eligible after exact source-ID/namespace import or keyed-live linkage, immutable full-payload comparison, source-owner `ready`, all applicable primary projections applied, and durable checkpoint/manifest verification. Delete only the verified bounded IDs; keep failures/pending rows. This proof is independent of unrelated active writer epochs. For ClickHouse's existing broad `created_at < cutoff` mutation, require complete multiset coverage plus a narrow no-late-write fence for that predicate during mutation; otherwise pause CH deletion or use a bounded manifest-aligned mutation. Never let an application-only check stand in for native TTL protection.
2. **Do not equate row cleanup with exact statistics.** No fact/log for an upstream occurrence lost before finalized Prepare means its numeric value is irrecoverable. An open/unknown epoch may signal that gap, but has no recoverable quantity. Row-level eligibility can permit deleting other verified persisted rows; global exactness, active-prefix certification, and rolling-24-hour cleanup claims stay false while applicable epoch/gap/manifest coverage is unresolved. Do not synthesize zero or replay finance.
3. **Use separate pending-read and retry indexes.** Retain the drain index `(source_state, applied_version, next_attempt_at, id)` for delayed due retries. Preserve normal fact-range indexes. Add global pending time-tail `(source_state, applied_version, kind, occurred_at, id)`; add the user-leading form only if a user tail query exists; preserve channel-tail index. Keep 1,001-row fail-not-ready sentinel and prove bounded plans in hosted DB runs.
4. **Preserve exact SQL semantics.** Native request/upstream exact text predicates use the existing native-compatible comparison and must not be excluded by byte digest unless byte-exact equivalence is proven per dialect/collation. Post-hit full-text checking cannot recover excluded case/trailing-space matches. Preserve substring/wildcard semantics and require real SQLite/MySQL/PostgreSQL parity before cutover.
5. **20 GB is an unclosed deployment capacity gate.** At declared text maxima (~27 KiB/event), 1.68M rows imply ~46 GB decimal of text alone, before indexes/projections/WAL; this is a worst-bound warning, not a typical-size forecast. On a representative authorized non-production copy, measure row/index and projection footprint plus peak migration/WAL/index-build space and live growth. Provision/expand primary capacity before backfill if measured peak plus reserve cannot fit. Log deletion does not immediately return PostgreSQL OS space; no savings/ratio is claimed. Capacity evidence and any ops reserve remain root/deployment acceptance, not a p4 production task.
6. **Keep conditional source behavior honest.** First source-owner confirmation attests the gross report outcome it just observed, not finance atomicity or a preexisting finance receipt. After lost process/outcome, require durable trustworthy evidence for the same occurrence or leave unknown; never auto-promote/re-debit. Midjourney effective token ID/final numeric payload is fixed before immutable Prepare.
7. **Schema draft stays frozen.** p5's `schema-claim-contract.md` and pJ's `write-backfill-architecture.md` are unchanged. These are p4 review recommendations for root's owned artifacts and later implementation acceptance, not an assignment to p5/pJ or source-code owners.
