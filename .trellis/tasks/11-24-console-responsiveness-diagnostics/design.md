# Design and boundaries
## Evidence
- Fingerprint requests page_size=30 but model.SearchChannels loads every match then controller slices. AfterFind adds one allocation SQL per migrated channel. Normal page listing/cache reload also trigger per-row queries.
- Channel Update synchronously reloads full cache and records audit before replying. BumpSyncTopic only records a task; it does not wait for other-node ACK.
- Invitation creates one transaction then synchronously resolves audit actor/cache and writes LOG_DB. Redemption creates up to100 rows sequentially then audits. Frontend create dialogs already close immediately after HTTP success.
- Probe DTO omits actual prompt/reply; generator/result already contain them. API Info uses configured array order and public status; instance collector already samples resources but full instance API is root-only.
## Architecture
1. Channel owner: bounded SQL queries and batch allocation projection for management and cache reads; lightweight authorized channel options DTO. Preserve authoritative entries elsewhere. Context flows into DB. Publish local route/binding state with revision/order safety, retain existing background sync.
2. Mutation owner: audit slow post-commit work, batch redemption writes, return committed result promptly; durable recoverable operation/batch identity for code creation so response loss/retry does not create a new batch. Reuse existing durable work mechanism where suitable; publish exact schema/interface before shared integration. Never background required auth/cache revocation or discard audit on process exit. Audit actor comes from authenticated request snapshot.
3. UI owner: use lightweight options API contract from keys; preserve identity-keyed caching/AbortSignal. Card quota uses billed channel.used_quota / configured local limit (known ledger-off/disabled/unconfigured limit is 0; a configured limit is shown only when both ledger and budget are enabled), reusing the shared quota formatter. R24 supersedes the previous log-backed token totals: migrate numeric readers only after durable persistence, historical reconciliation and hosted evidence are ready. Name replaces the full card type slot, while table type remains. Relative time reuses the existing helper, with unclipped responsive labels/values. Probe strings copied into existing bounded job snapshots and rendered in shared Card/CopyButton.
4. Dashboard owner: stable instance node_name binding can be referenced by multiple configured API entries; persist ordering in existing API settings. Batch resource projection exposes only configured instances' approved CPU/memory/storage/status/timestamps. Full root instance API permissions remain. Track sample validity, never equate unavailable to0.
5. Ranking: extend existing aggregation for selected model/time window with bounded users; filter names/identity at server according to viewer. Reuse existing model detail drawer shell, usage formats and model authorization. Never share privileged DTO caches across identities.

## Rollout
Preserve old clients/settings with optional additive fields. No domains infer traffic behavior. Validate schema/locking in cloud across engines. Revert independent UI surfaces or service contracts coherently; never remove committed budgets/audits/created codes during rollback.

## R21 boundary: session admission and restoration
- Gap: default 50-session admission rejects authenticated logins while unexpired SQL rows from inaccessible or stale-auth-version sessions still count. Both the primary service path and the transactional verification-flow path enforce this policy.
- Change owner: `common/constants.go` / `common/init.go` define zero as the default unlimited concurrent-session policy; `service/auth_session.go` / `model/login_verification.go` skip the active-count query only when unlimited. Preserve the independent rolling issuance limit and all verification transactions.
- Extend existing configuration/service/security-login tests; CI explicitly exercises real relational engines and focused races. No schema change, forced device eviction, unauthenticated session cleanup, credential reuse by IP/User-Agent, or authentication bypass.
- Restart investigation: a process-random `SessionSecret` without a fixed shared environment setting is a source-supported invalidation condition, not confirmed production configuration. Browser restoration is independently reviewed before any additional source change.
- Applicable guidance: OWASP ASVS 5.0.0 V7.1.2 treats concurrent-session count and overflow as documented application policy. Authentication and Session Management Cheat Sheets require retaining authentication, secure session identifiers, expiry/rotation/revocation and logout controls. No full ASVS compliance claim.
- User clarification: an unusable session must not consume an active-session slot even when a positive cap is explicitly configured. Count and list require current authoritative user auth version, active status, zero revocation timestamp and future expiry. The MFA transaction uses its locked user state. Preserve historical rows and all-status issuance accounting; no cleanup is needed to make an invalid row stop counting.
- Confirmed restoration defect: `RefreshLoginSession` classified every session lookup failure as an invalid refresh token, causing `RefreshAuth` to clear cookies on temporary DB failure. Only a missing row maps to invalid credentials; inactive rows remain revoked, while operational failures propagate to the existing generic 500 without clearing cookies. A retry must refresh the same session with the original cookie.
- Browser guards currently treat a transient refresh failure as anonymous. Preserve the requested route and use the existing recoverable route error/retry UI until authentication is resolved. Confirmed anonymous users still reach sign-in; protected content never renders while unresolved.

## R22 boundary: per-Key catalog additions and editor controls
- Fetch remains read-only and Save remains explicit. The selected Key editor may select newly discovered upstream models. Saving an allowlist adds only its normalized selected model names to the existing channel catalog, preserving existing order, manual models, other Key scopes and an explicit empty allowlist as deny-all.
- Use the live allocation handler and its existing `MutateChannelKeyEntries` transaction. Validate stable Key ID and expected revision before catalog additions; persist the selected entry, additive catalog and abilities together. Enqueue a secret-free `channel.multi_key_manage` audit draft inside that transaction and fail the write if enqueue fails; mark the request audited once after success. Existing sync/publication behavior remains, with no claim that its post-commit sync bump becomes transactional.
- Return authoritative `channel_models` from the committed channel. The existing manager updates its current row only after successful Save. Do not add a second channel update, nest the full config update API under the polling lock, or perform all-Key upstream sync implicitly.
- Quota and Bind User controls retain sensitive-write permissions, ledger availability, stable identity/revision and conflict checks. Correct editor reachability through existing shared dialog/table composition; do not bypass disabled guards.
- Explicit diagnostic Key selection also requires stable identity. Add optional `key_entry_id` and `expected_rev` to the existing manual test endpoint, validate the authoritative allocation before dispatch and again after capacity admission, and preserve existing index-only clients and automatic/background behavior. Frontend results must not cross Key identities. A frontend metadata refetch alone cannot close the server reorder race.
- Discovery responses are tied to the editor request generation and selected identity. Closing or changing channel/Key/revision invalidates success, error, conflict and finally callbacks, so an obsolete conflict cannot reload an old channel into the current manager.

## R17 storage follow-up (2026-11-26)
Use a 3-day default only when the request-content retention setting is absent; explicitly persisted 0 remains keep-forever. Preserve the usage-log setting independently. The committed codec uses `newapi-request-content:gzip:v1:` plus base64, gzip BestSpeed for payloads at least 4 KiB, only when the complete encoded representation saves at least one eighth. Preserve original CapturedBytes/Truncated; decode after exact surviving-log linkage and protection checks, independent of the write flag. Bound encoded/compressed/captured data to 128 MiB, accept one strict complete gzip member and a valid JSON object, reject corrupt/partial data with a fixed value-free error. Old raw JSON, including CapturedBytes=0, remains readable independent of today's capture cap.

`REQUEST_CONTENT_LOG_COMPRESSION_ENABLED` defaults true. During a rolling upgrade, keep it false until all readers support the decoder; false only stops new encoding and does not convert stored envelopes. Rollback must use a decoder-capable build. No historical rewrite, physical-disk benefit claim, cleanup-throughput expansion or production operation. Existing relational/ClickHouse storage/driver matrices and fresh/released-upgrade-twice evidence remain required on the exact captured tree.

### R5 preview and dispatch contract

Use a bounded process-local opaque preview ID rather than a client-authored or signed challenge payload. Preview generation performs no upstream call and freezes the actual SDK challenges with owner, channel, model, endpoint intent, count and optional stable Key entry ID/revision. `POST /api/channel/:id/fingerprint/preview` returns the ID, expiry, selection and actual probes (`id`, `prompt`, `expected_count`). HTTP Start requires that ID and matching selection; it validates current Key identity/scope and executes exactly those challenges. Automatic Key selection remains explicit; a chosen Key must never silently fall back.

Under one registry lock, bind an accepted preview to its job before starting work. A repeat Start returns that job without launching more probes. Expired, removed, restarted or other-process previews fail closed with zero upstream calls; an evicted completed job cannot restart its preview. Bound unstarted previews to five minutes, 128 globally and four per owner; retain started bindings for job TTL plus maximum run lifetime and never evict active jobs. Preserve internal 24000-token budget, at most three probes, output cap 4096, scoring and cancellation.

The existing job registry remains process-local. Console forwarding to one configured master provides consistent routing; without it, callers require affinity or may receive an explicit unavailable preview/job error. This contract does not claim cluster-portable previews or restart recovery. The route matcher treats dynamic segments independently of their parameter spelling; `:job` versus `:job_id` is not a defect. Frontend retry after an uncertain Start reuses the same preview, never silently generates a new paid run.

### R19 build-origin default

Resolve update repository in order: explicit stored setting, validated nonempty `NEW_API_UPDATE_SOURCE_REPOSITORY`, validated nonempty build default, then the unchanged `QuantumNous/new-api` fallback. The build default is the exported string `github.com/QuantumNous/new-api/setting/system_setting.UpdateSourceBuildDefaultRepository`, set with Go `-X`. Fork image builds pass `github.repository` through Docker `UPDATE_SOURCE_REPOSITORY`; all four downloadable release binaries receive the same value. Ordinary builds with no binding retain upstream fallback. No production setting is overwritten.
