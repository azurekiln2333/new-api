# Upstream price synchronization performance research

Date: 2026-11-20 (Asia/Shanghai). Research only; no product code or tests changed.

## User-visible problem

With many models selected, opening **Preview price changes** is slow and **Confirm Changes** appears to freeze the UI. The same `UpstreamRatioSync` serves the model-list dialog (`web/src/features/models/components/dialogs/price-sync-dialog.tsx:24`) and system settings (`web/src/features/system-settings/models/ratio-settings-card.tsx:524`). Both entry points belong in acceptance.

## Confirmed code findings

1. **Repeated full-catalog serialization before opening the preview.** `handleApplySync` synchronously prepares all conflicts, calls `applyPriceSyncSelections`, builds the changes, and only then opens the dialog (`web/src/features/system-settings/models/upstream-ratio-sync.tsx:321-378`). `applyPriceSyncSelections` iterates selected models and calls `applyPricingValues` once per model (`web/src/features/model-pricing/pricing.ts:364-401`). Each call parses and serializes every one of the eleven pricing-option maps (`pricing.ts:290-329`), including unchanged provider maps. For S selected models and N existing entries, this repeats work proportional to S × N instead of parsing the catalog once. The per-model validation path also round-trips one-model maps via `pricingRow`/`pricingRows` (`pricing.ts:199-230,395`).

2. **Preview renders every selected model.** `ConflictConfirmDialog` passes the entire conflicts array to `StaticDataTable` (`web/src/features/system-settings/models/conflict-confirm-dialog.tsx:74`). Its implementation does unconditional `data.map` (`web/src/components/data-table/static/static-data-table.tsx:107`) with no paging or windowing. A `max-h-96 overflow-y-auto` viewport limits visible height, not mounted rows. Primitive/model/current cells also create shared Tooltip components through `TruncatedCell` (`static-data-table.tsx:182-191`; `core/truncated-cell.tsx:64`). The dialog's inline columns and lack of a memo boundary cause this large tree to render again when saving status changes.

3. **Display preparation repeats expression parsing.** For each selected model, the apply handler formats current, saved USD, and optional site-currency prices; the site-currency eligibility check independently calls `getSyncExpressionPricing` (`upstream-ratio-sync.tsx:344-351`). `describeSyncPrice` also calls this parser (`upstream-ratio-sync-helpers.ts:161,211`). Formatting all rows before showing any UI is avoidable. The payload must still be validated as a whole before confirmation becomes available.

4. **Confirm already uses one async HTTP request.** `syncMutation.mutationFn` posts the previously frozen `confirmed.changes` (`upstream-ratio-sync.tsx:229-233`; `web/src/features/model-pricing/api.ts:161`). There is no synchronous per-model save request loop in the handler. A browser Worker cannot eliminate an oversized React/DOM commit or server latency. Do not claim the confirmation hang is proven to be purely CPU or purely network without a browser trace.

5. **Saving triggers avoidable extra UI work and extended pending state.** Pending-state changes re-render the full preview. On success, code replaces every price-row object, clears selections, closes the dialog, waits for five families of query invalidation, then fetches the full baseline again (`upstream-ratio-sync.tsx:234-253`; `api.ts:151-158`). The settings parent already subscribes to `useModelPricing()` (`ratio-settings-card.tsx:180`), so invalidation may fetch a baseline before the explicit subsequent `getModelPricing()` fetch. Query invalidation and baseline loading must be coordinated rather than silently dropping refreshes.

6. **The main comparison list already paginates.** `upstream-ratio-sync-table.tsx:166-174` uses shared `useDataTable` with a ten-row page; its desktop/mobile renderers and `DataTablePagination` already exist. The preview is the concrete unbounded DOM path. The comparison list still recalculates filtering/sorting/bulk selection across all models on relevant changes (`:85-164`), so inspect those costs after fixing the larger hotspots.

7. **Server save is atomic and version checked.** `controller/model_pricing_config.go:68-91` passes one batch to `model.UpdateModelPricing` and returns updated model names. `model/model_pricing_config.go:630-661` checks per-model expected versions and validates drafts inside `mutateModelPricingOptions`; the latter performs a single transaction (`:704-763`). Do not split the client save into unrelated per-model PATCHes as a performance workaround. Server-side expression validation and provider-map scans may contribute latency for large batches (`:128-171,502-628`), but were not profiled and are not established as the main blocker.

## Recommended implementation scope

1. Rewrite the sync batch operation to parse each catalog map once, validate/normalize each selected bundle, apply all bundles to those mutable working maps, and serialize once. Preserve the shared public behavior; avoid a parallel pricing semantics implementation. Preserve prototype-safe model keys (the current writer deliberately uses `Object.defineProperty`), explicit zero values, omitted-value removal, literal upstream expression text, provider overrides, and fixed/token/expression mode cleanup.
2. Keep the existing `ConfirmDialog`. Compose shared `useDataTable`, `DataTableView`, and `DataTablePagination` for a bounded preview page, including model-name search and the full selected-count summary. This is an existing reusable capability and avoids introducing a custom virtualization framework. If uninterrupted scrolling is chosen later, the installed `@tanstack/react-virtual` could be composed into the feature, but no existing virtual-list implementation was found under `web/src`; do not replace shared table infrastructure casually.
3. Freeze raw selected records, adjusted prices, currency/rate, expected versions, and the exact save payload together. Format visible preview rows lazily from this immutable snapshot instead of eagerly formatting the complete catalog. Keep complete reviewability through paging/search; never silently truncate the selection or save only the visible page. Language-dependent labels may re-render, but exchange-rate changes while previewing must not alter the confirmed charge.
4. Show an immediate preparing/saving state and suppress repeated actions. Chunk remaining expensive pure work with yielding, or move the isolated pure preparation to a Web Worker **if profiling after the algorithmic fix still shows long tasks**. A Worker should receive plain price data, not credentials, HTTP clients, React state, or translation functions. Include job identity/stale-result rejection and cancellation on unmount/new selection; no result may overwrite a newer preview. React scheduling can defer commits but does not remove synchronous JavaScript work performed while preparing data.
5. Keep one atomic server save with the frozen payload. Separate save completion from follow-up refresh state; reuse React Query's pricing cache/fetch to avoid duplicate full baseline loads. Maintain stale-version handling and block the next save until an authoritative baseline is available. Background refresh errors must not misreport an already committed batch as a failed save.
6. Profile the actual confirmation action. If request wait dominates, report it separately; only extend into backend save optimization with evidence and the mandated SQLite/MySQL/PostgreSQL validation. No backend/database change is needed just to fix full-table rendering and repeated frontend serialization.
