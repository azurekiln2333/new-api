# 通用日志请求内容与节点诊断

## 目标

管理员打开通用日志即可排查一次请求的原始提示内容和实际处理节点；成功与失败都可查，且列表不携带大段正文。

本文件是父任务 R6/R7 的交付要求。当前仅完成方案设计；以下方案口径交由父任务最终统一审阅，不表示已开始实施。

## 已确认事实

- 普通成功和失败日志没有统一保存原始 prompt/messages 或 NODE_NAME。现有参数覆盖审计、插件变更记录不能还原原始请求。依据 service/log_info_generate.go:70、service/relay_error.go:187。
- 日志 other 有角色裁剪；普通用户日志的 id 可能被重写成页内序号，不能据此读取正文。依据 model/log_other.go:232、model/log.go:137。
- 请求可能在 controller.Relay 之前被协议准备或插件改写，原始快照必须早于这些阶段。依据 router/task-plugin-protocol-router.go:34、controller/relay.go:156。
- 日志库可能独立配置为 SQLite/MySQL/PostgreSQL/ClickHouse；其迁移、清理与正文必须覆盖同一日志库。依据 model/main.go:407。

## 需求

- R6.1：保存客户端入站请求中的提示文本与结构。Chat/Completions 覆盖 messages/prompt；同类协议覆盖 Responses input/instructions、Claude messages/system、Gemini contents/systemInstruction；multipart 仅保存相关文本表单字段。
- R6.2：成功日志、现有渠道尝试失败日志，以及鉴权成功后参数错误、无可用渠道、模型限流等最终拒绝日志都能显示采集结果。一次入站请求重试共享一份原始快照。
- R6.3：详情按需读取正文；列表、统计、现有导出及普通进程日志不携正文。内容状态至少能区分已记录、截断、无相关文本、类型不支持、无效/无法读取、未开启、保存失败、历史未记录和已清理。
- R6.4：正文读取采用与管理端通用日志相同的 admin/root 服务端权限；普通用户及模型 API 令牌不能用引用越权读取。沿用现有个人访问令牌的 log:read 范围检查。
- R6.5：方案提供独立环境开关 REQUEST_CONTENT_LOG_ENABLED，默认开启以满足本次明确记录要求；REQUEST_CONTENT_LOG_MAX_BYTES 默认 262144（256 KiB），可配置。超过上限时保留有界、有效的文本/JSON 摘要并标示截断。
- R6.6：正文与其关联日志沿用相同保留与清理策略，不引入额外 7 天保留期限。清理一条重试错误日志不能破坏仍存在成功/其它错误日志的共用正文。
- R7.1：每条日志的 admin_info.node_name 保存该次业务操作实际处理实例的 NODE_NAME，桌面列表、移动列表和详情都显示。不能用查询节点、代理节点、数据库节点或原任务提交节点替代。HTTP 同节点重试通常仍是同一值。
- R7.2：原始正文快照及 TaskPrivateData 独立保存 submit_node_name，表示接收入站请求/提交任务的来源节点。异步 poll/settle 若在另一节点执行，日志处理节点写执行节点，详情另显示提交节点；保留原始正文和请求 ID。Responses WebSocket 每个 response.create 关联各自的原始提示内容。

## 关键方案口径

- 只采集提示文本相关白名单字段，媒体二进制、base64 和文件本体以类型/大小标记替代。不采集请求头或任意凭据字段。
- 先捕获到独立受限快照，再随符合日志开关的日志或将需后续日志引用的已接收活动任务保存；不为完全关闭的成功/失败日志单独长期保存正文。
- 记录失败不改变推理结果、退款或结算。现有日志开关及错误过滤保留；补齐的鉴权后最终拒绝有一次性标记，避免重复制造最终错误行。
- 新正文只开放管理端诊断；普通用户自己的消费摘要范围保持现状。每条日志的处理节点作为 admin_info.node_name 展示；历史任务 root_info.node_name 只能按原权限作为提交来源回退，不能冒充处理节点。

## 验收标准

- AC1（R6.1/R6.2）：含不同角色及多段内容的有效请求，经过插件/参数覆盖后日志仍显示原始值；成功和上述失败路径能按稳定引用读到同一份原始快照。
- AC2（R6.3/R6.5）：大正文、附件、无效 JSON、未开启、存储失败、旧日志和清理后场景均有准确状态；列表和进程日志不能出现正文或附件内容。
- AC3（R6.4）：匿名、普通用户、模型 API 令牌、缺 log:read 的管理 PAT 均不能获取正文；admin/root 在现有权限下可读取，伪造或已清理引用不能泄露其它数据。
- AC4（R7）：五个节点写入后，从任意节点查询均显示当次日志的真正处理节点。HK 提交、US 结算时，结算日志处理节点为 US，正文提交节点仍为 HK，详情两者分开；WebSocket 多次 response.create 不混淆原请求。
- AC5（R6.6）：重复日志共用正文可读取；仍有关联日志、活动任务或正在关联的请求时不提前清理；最后引用消失且无未决写入后由有界回收清除正文。ClickHouse 日志 TTL 与手工清理均覆盖详情，正常路径的物理删除允许一个清理调度间隔；协调故障时保持保护并可恢复，不能提前删除。
- AC6：SQLite、MySQL、PostgreSQL 真实实例验证新建/升级、两次启动、读取、清理和故障路径；ClickHouse 日志库另外验证建表、详情读取、重复故障提交读取、日志 TTL 后回收与写入/回收交错。
- AC7：详情在桌面/移动端可滚动、复制并正确显示加载/失败/截断；七种语言文案、类型检查、lint 和相关测试通过。

## 范围外

- 不记录模型回复全文、请求头、认证凭据、媒体二进制或完整连续 Realtime 音频/事件流。
- 不把匿名鉴权拒绝、登录或管理接口请求体写成通用推理日志。
- 不伪造、恢复历史缺失正文或节点；不实施 HK-US 延迟架构重构。

## 依赖与交付

本子任务可独立于 Key 配额功能实现和验收；共享 controller/relay.go、service/log_info_generate.go 等文件时由父任务协调顺序。Key 条目 ID 若新增，可作为另一条轻量诊断字段接入，不阻塞本任务的正文引用。设计和执行顺序分别见 design.md、implement.md。
