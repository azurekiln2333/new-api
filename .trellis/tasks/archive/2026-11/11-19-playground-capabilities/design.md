## Playground and upstream endpoints (R1-R5)

Reuse ModelGroupSelector, prompt tools, parameter controls and Message.sources. Search defaults off; send the existing web_search_options intent with existing medium context default, preserve annotations from JSON and SSE, deduplicate sources, retain cancellation/history and existing usage billing. An unsupported explicit search must not silently disappear. No independent search service or new prices.

Keep browser requests on /pg/chat/completions. Add an optional channel declaration of supported upstream endpoints to the existing settings JSON, initially covering the normal OpenAI-compatible Chat/Responses adapters. UI offers Chat, Responses, or both; an absent setting preserves legacy behavior. It is an upstream capability declaration, not an inbound route allowlist. Do not substitute an unrelated tri-state playground preference. AdvancedCustom route contracts remain their own source of truth.

Resolve the outbound target once per attempt: explicit supported endpoints constrain all choices; prefer a supported native endpoint, honor the existing global conversion preference only when its target is supported, otherwise use an existing supported conversion. Thus Responses-only always maps Chat/Messages to Responses, Chat-only cannot accidentally select Responses from global policy, and Chat+Responses retains compatible native routing. Reuse textRequestViaResponses, request converters and response conversion back to the incoming client format. Validate unsupported adapters/settings and conflicting channel passthrough at save time. Global passthrough conflicts must be detected at request selection/runtime rather than silently sending the wrong payload. No automatic UA guessing; preserve configured header templates.

Channel navigation is admin-only and uses a real server-validated pin with group/model/user-bound-key eligibility. Minimal channel metadata must exclude credentials and overrides. Returning to groups clears the pin. Invalid/pinned selections must not silently fail over. Sort a copy with fixed valid en Intl.Collator(numeric:true, sensitivity:base) plus raw-ID tie-break; preserve selected model.

Record conversion chains for both consume and error logs. Missing old metadata is unknown, not proof of Native format. Preserve inbound seed and final target; do not report a conversion that did not occur.

## Admission, metrics, failover and waiting (R6-R8)

Use one lease lifecycle for limited and unlimited channels: zero/unset means no cap, not no accounting. Preserve detached-submission ownership, idempotent release, cancellation and Redis lease expiry. Memory mode reports this instance; Redis mode reports the coordinator's cluster scope. No per-request database counters. Avoid creating a parallel increment/decrement metric that drifts from admission.

Unlimited-channel telemetry is best effort: a Redis admission/renewal error must not reject or cancel a previously unlimited request merely because counting was added. Keep its local owner lifecycle, mark the cluster metric unavailable/incomplete, and reconcile still-active owners after recovery before claiming a complete cluster sample; drained owners must never be resurrected. Limited channels retain the existing fail-closed capacity-coordination behavior. Queue-coordinator failures are explicit service errors, not false full/zero capacity. Test admission, renewal, cancellation and post-recovery metrics for both modes.

One bounded admin batch API returns id, current (nullable), limit (null=unlimited), scope and sample time for visible channel IDs. In Redis count unexpired lease scores against Redis server time using pipelined read scripts; no key scans or reap-on-every-dashboard-read. A Redis error is unavailable, not zero. Local read takes one map snapshot. Reuse current channel authorization/loaded settings. Account for tag aggregates explicitly; do not invent a channel ID for a tag.

Frontend uses a single visible-set subscription including an open drawer ID, normalized shared entries and one 5-second refresh timer. Cards never poll individually; opening a visible card's details consumes the same sample. Pause hidden pages and closed/unmounted views; retain last-known sample with stale/unavailable presentation. Counters are sampled and Redis crashed leases may persist up to their TTL. Measure unlimited-path added work and coordinator connection use.

For failover, classify local admission saturation, explicit upstream concurrency rejection, general rate-limit 429, quota exhaustion, transport failure and cancellation separately. Preserve ordinary status-policy behavior for other errors. The native Responses handler must return a real pre-output failure for response.failed/error or required-terminal premature EOF rather than returning nil success. Retain original error code/message and do not auto-ban a channel on an ambiguous substring.

Before delivering any attempt-identifying/model output, stage only a bounded amount of protocol initialization. On early busy/error, discard that attempt's buffer and select another eligible candidate. Once an attempt's response ID, model content, reasoning, tool delta or other irreversible event is exposed, no replay/failover: finish with protocol-correct error and actual partial usage. Never simply remove Writer.Written guards.

When all eligible candidates are busy, enter a deliberate outer waiting state. Local cap release wakes eligible FIFO waiters; Redis uses shared coordinator notifications with bounded recovery polling, cancellation leases and an atomic admission recheck. Do not hold one Redis blocking connection per waiter, drop live tickets with LTRIM, or broadcast unlimited retries. Queue release is not permission to bypass current group/key/channel policy; re-evaluate after wakeup. Pins/strict affinity wait on their allowed channel.

Recognized upstream concurrency errors without a local cap are in scope: the same pending request waits under a per-channel gate, honors Retry-After when meaningful and uses bounded jittered backoff/single-probe admission. The gateway cannot observe upstream slots occupied by other clients; do not claim exact upstream capacity or strict global fairness there. Quota exhaustion and generic 429 do not become endless capacity queues.

Proposed final-review defaults: waiting enabled, 300 seconds max waiting, 1,000 queued requests per coordinator and 20 per authenticated user, configurable; resource overflow/deadline produces a clear retryable busy outcome. No ordinary saturation immediate disconnect. Client cancel removes the waiter and returns any raced reservation. Queue time is separate from per-attempt first-byte timeout; repeated waiting must not double-reserve or double-settle quota. Initial local waiting happens before billing preparation. If an upstream attempt already reserved quota before returning busy, preserve the existing request-scoped reservation/settlement contract explicitly: no second reserve merely for a wake/retry, no lost refund on cancel, and no invented zero usage for a failed attempt that actually reported billable usage. Do not move pre-consume after upstream execution or after model output.

For SSE waiting, protocol-valid comments can keep the connection alive without an attempt ID. This requires a dedicated outer response state distinguishing uncommitted, keepalive-only, and attempt-output-started. Ordinary retry code still obeys Writer.Written; only the audited outer orchestration may start a fresh upstream attempt under a keepalive-only envelope of the same protocol. After comments commit HTTP 200, terminal failures use the existing protocol's stream error rather than trying to change HTTP status. Non-stream requests wait without fake SSE. Proxy/client timeouts remain external limits; new-api cannot command a client's reconnecting label. Validate each supported streaming protocol and keep the writer serialized.

## Goal-aware candidate restrictions (R17)

Reuse channel constraints/candidate filtering after normal model/group/key eligibility. Classify incoming request features once and retain the reason for all candidates excluded. Unsupported candidates are skipped without an upstream call; an explicit pin that violates policy is locally rejected, not silently overridden.

Official current Codex source provides turn_trigger="goal" inside the JSON string at client_metadata["x-codex-turn-metadata"], plus a compatibility header. Parse bounded structured data; for WebSockets prefer per-message metadata to connection metadata. Do not infer active goals from tools get_goal/create_goal/update_goal (they can be advertised while inactive), User-Agent alone, or arbitrary text containing goal.

This reliably defines recognized goal-triggered turns; older clients, manual steering, subagents or stripped metadata are not completely detectable at the gateway. State that limit in setting help and final acceptance; never claim complete detection of all goal-associated activity. Preserve unrelated metadata in relay. If stricter client cooperation is desired, it is a separate explicit marker contract, not fabricated existing behavior.

## Credentials, CORS and avatars (R18-R20, R23)

Reuse existing ownership, step-up verification, origin/CSRF and audit mechanisms. Rotate an existing key record atomically, preserving ID/permissions/limits/history, and invalidate old credential caches across supported deployments. Concurrent rotations and duplicate custom keys must fail safely without revealing another owner's record. New credentials are never written to logs, task artifacts or audit payloads.

Custom-secret contract proposed for final review: accept an optional leading sk- and store the remaining 32-128 ASCII letters/digits, with at least eight distinct characters; reject whitespace/control characters, embedded separators, the current secret on rotation, duplicates, common trivial sequences and a whole value formed by repeating a motif of up to 16 characters. Embedded hyphens are forbidden because middleware/auth.go currently parses them as routing suffixes. Enforce these rules on the server and test maximum storage length and each database's uniqueness behavior. The ordinary secure random 48-character generator remains default. Length/variety checks reject obvious weak values but do not prove entropy; do not claim user-chosen strings are equivalent to generated secrets or expand API-key rights. Custom create/reset is available only for the authenticated owner's keys, with the same sensitive-action protections; return the result through the existing guarded reveal/one-time result flow, never audit the value.

CORS allowlist must use configured exact origins (scheme/host/port), with site's configured public origin as the safe base and explicit additional origins. Reject wildcard/null/malformed entries, never echo arbitrary Origin or trust Host/X-Forwarded-Host to authorize it. Keep no-Origin CLI/API requests working. Separate browser session origin protection from CORS response permissions; reuse auth-origin normalization where semantically appropriate without treating OAuth redirect allowlists as a general API list. Include PATCH/actual required headers, Vary: Origin and allowed/denied preflight tests. Actual site origin is deployment input; the upstream provider URL is not evidence of this site's origin.

LinuxDO successful-login avatar sync reuses OAuthUser.AvatarURL, AvatarProvider and SyncUserAvatar, which already run after successful authentication. Existing policy is provider-sourced avatars; no user-editable custom-avatar UI was found. Verify the real LinuxDO userinfo claim or supported avatar endpoint before enabling its marker interface, so an absent unsupported claim does not clear a stored avatar. Normalize URLs, bound any new fetch/redirect, no auth token sent to image hosts, and avatar failures never prevent login. Preserve OAuth state, linking, MFA/step-up and session assurance.

Current OWASP references/ASVS controls and failure tests are required before auth edits. New database mutations require SQLite/MySQL/PostgreSQL verification even with no migration.

## Official status and local fingerprint detection (R21-R22)

Reuse sidebar/theme/cards/empty states. Official status is separate from gateway health: bounded server-side polling of an explicit official-source catalog, cached about five minutes, retaining last-success timestamps and stale/unknown states. No request-supplied fetch URL/SSRF surface. Do not depend on tcping's undocumented internal API; include the user's exact disclaimer as the Chinese translation of an English i18n key. Do not overload /api/status's existing login/public-status contract.

Fingerprint page uses a pinned reviewed lm-detector Go SDK and local reference assets with checksums/version and preserved license notices. No mandatory runtime fetch from lm.ikale.io, no channel key in the browser or third-party proxy. Do not import their entire website. Reuse channel-test authorization, eligible keys, endpoint conversion, capacity and timeout handling for bounded admin-triggered multi-probe runs. Default tokenizer extra probes off; explicit run start, visible estimated cost/progress/cancel, per-run token/request caps. Persist results only if required by the accepted UI contract; otherwise avoid a new database schema.

Output is a reference-bank-relative statistical ranking with confidence limitations, not an IQ score or authenticity assertion. Invalid/insufficient samples may show an inconclusive result, but an unenrolled model can still receive a closest candidate: do not promise out-of-bank detection or invent an abstention threshold without validation. Verify SDK results with its known fixtures, serialization/probe compatibility and cancellation/budget regressions.

## Commits, delivery and rollback (R25)

Root owns the Git index. Record the pre-existing dirty baseline and never stage it incidentally. Each R item has one focused product commit with tests/needed translations; shared files are handed over sequentially. Subsequent review fixes reference the owning item in a separate small commit, never rewrite published history. Shared dependencies are recorded so rollback can revert in reverse dependency order.

Previous merge/workflow repairs already in the working tree belong to their own task and must be independently reviewed/committed if required for the final build; a clean feature diff atop dirty dependencies is not a releasable commit. Validate the exact committed tree in an isolated checkout/worktree before publishing.

The fork release path is push to fork/main after the integration branch checks, not tag-only. Recheck remote ancestry and use ordinary fast-forward pushes; do not force-update shared branches or tags. The workflow creates the custom version tag/release, architecture images and assets; verify exact source SHA, tag target, image digest and successful jobs. Then inspect the identified server's image reference, pull/run only the application service, compare /api/status version and health, retain old digest for rollback. No database/Redis restart or destructive data rollback.

Server target/path/public origin is currently requested from the user; absence blocks live deployment verification. Never infer it from the upstream API. The repository template's calciumion image and the fork GHCR image differ and must be reconciled on the actual deployment. Final handoff is a requirement-to-commit/check map plus CI/image/server observations, not a generic completion claim.

Freeze the deployed product SHA before publication. After deployment, commit verification/report/journal bookkeeping separately on merge/upstream and, if pushed, push that branch only; do not push the bookkeeping-only commit to main and trigger an endless new release. Report the deployed product SHA and later bookkeeping SHA separately. Include bookkeeping in a future normal release; never fabricate or rewrite a release tag to cover it.
