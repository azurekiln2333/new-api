# 渠道 Key 级授权与分组模型可见性

## 目标

让一个渠道就能表达「不同 key 给不同用户、不同 key 跑不同模型、不同分组看到不同模型」，不必为此拆成多个渠道、多个分组。改动以最小为原则：不新增表、不新增列。

## 需求

- **R1 Key 绑定用户**：多 key 渠道里的某个 key 可以绑定给一个用户。绑定后该 key 只给这个用户用，其他人轮不到它。用户所在分组不变；即使用户的分组不在该渠道的分组里，他也能通过这个 key 使用该渠道的模型。
- **R2 分组模型可见性**：一个渠道的模型可以按分组设置可见范围。例：渠道有模型 A、B，分组甲只见 A，分组乙见 A 和 B。不可见即不可用（模型列表里没有，请求也不会路由到该渠道）。未设置的分组看到渠道全部模型。
- **R3 单 key 转多 key**：已创建的单 key 渠道可以在编辑时转成多 key 渠道，原 key 保留为第一个 key。
- **R4 Key 级可用模型**：多 key 渠道里每个 key 可以设置自己能用的模型（渠道模型的子集）。未设置的 key 可用渠道全部模型。请求某模型时只会选到能用该模型的 key。

- **R5 渠道卡片跳转按钮**（追加）：渠道卡片上加一个小按钮，点一下在新标签页打开该渠道的地址（渠道的 base URL）。样式、尺寸、图标风格、悬停提示与卡片上现有的操作按钮一致。渠道没有填地址时不显示该按钮。纯前端改动。

## 已定口径（需求里没写明的地方，按下面执行）

1. 绑定是独占的：绑定给用户的 key 不进公共轮询。一个 key 只绑一个用户；一个用户可以在多个渠道、多个 key 上有绑定。
2. 用户有可用的绑定 key 时优先走绑定 key；绑定 key 不覆盖所请求模型时，走原来的分组路由。绑定渠道请求失败后的重试沿用现有重试逻辑（即回落到分组渠道，分组没有该模型就按现有方式报错）。
3. 计费口径不变：倍率仍按用户/令牌当前使用的分组计算。本任务不改任何计费代码。
4. 用户的模型列表（`/v1/models` 及控制台里用户可用模型列表）要包含他绑定 key 带来的模型。模型广场/定价页按分组展示，不体现个人绑定，本任务不改。
5. 只做单 key → 多 key，不做反向转换。
6. 令牌自身的模型限制、管理员令牌指定渠道等既有限制继续生效，优先级不变。

## 验收标准

- [ ] AC1：给多 key 渠道的 key#2 绑定用户 U 后，U 请求该 key 支持的模型时用的是 key#2；其他用户请求同一模型永远不会用到 key#2。
- [ ] AC2：U 的分组不在该渠道分组内时，U 仍能请求成功，且 `/v1/models` 里能看到绑定 key 带来的模型；解绑后立即恢复为原分组行为。
- [ ] AC3：渠道全部 key 都已绑定用户时，该渠道不再对任何分组提供模型（没有公共 key）。
- [ ] AC4：渠道模型 A、B，分组甲只允许 A：分组甲的模型列表没有 B，分组甲请求 B 不会路由到该渠道；分组乙不受影响。
- [ ] AC5：单 key 渠道编辑后可转为多 key，原 key 仍可用，随后可追加 key、进入多 key 管理。
- [ ] AC6：key#1 只允许模型 A、key#2 只允许模型 B：请求 A 只用 key#1，请求 B 只用 key#2。渠道测试指定模型时也选对 key，不会因选错 key 而误判失败、误禁用。
- [ ] AC7：删除、追加、覆盖 key 之后，key 的可用模型和绑定用户仍跟着原来那把 key 走，不会错位到别的 key 上。
- [ ] AC8：某模型暂时没有可用 key（例如唯一支持它的 key 被禁用）时，请求得到可重试的错误并能换渠道，渠道本身不会因此被自动禁用。
- [ ] AC9：未使用任何新配置的既有渠道，行为与改动前完全一致（abilities 生成结果、key 选择、模型列表均不变）。
- [ ] AC10：没有数据库表结构变更；前端新增文案七种语言齐全；CI 在本机对应的检查全部通过。
- [ ] AC11：渠道卡片上有跳转按钮，点击在新标签页打开渠道地址；外观与同一卡片上的其它按钮一致；无地址的渠道不显示；文案七种语言齐全。

## 不做

- 新增表或列、数据迁移。
- 计费、定价页、模型广场。
- 多 key → 单 key 转换；按 key 的限速、配额。
- `docs/` 下新增文档。
