# Allocation identity and budget accounting

Proposed design for parent review. The Key and manual channel budget tasks share the persistence and settlement contract below.

## Allocation records

Create `channel_key_entries` for managed allocations with a GORM-generated 64-bit ID, channel ID, position, existing credential or managed credential reference, bound user ID (zero is public), model scope mode and a normalized TEXT allowlist, status/reason/time, configuration revision and retirement timestamp. A single-Key channel can have an internally addressed allocation where necessary for the shared lifecycle. Public APIs and logs may carry stable IDs but do not gain permission to return credential material. DTOs use decimal strings for 64-bit IDs where needed to preserve JavaScript precision.

Migrate the original `Channel.Key` and `ChannelInfo` by original index, including existing equal credential occurrences and historical disabled state. Backfill once under the channel lock and retain a migration marker, including for empty channels. Preserve the old fields as a compatibility projection during rollout. Once active, allocation rows are authoritative. Writes to the old fields go through an allocation-aware transaction and cannot reconstruct IDs by first text match. When a legacy single-Key edit remains unambiguous, preserve its existing ID. For multiple equal entries require explicit IDs and revision for edits, moves, deletes and delayed apply. Append creates a new ID each time. A full raw replacement that cannot prove which allocation to preserve returns a conflict and reload instruction.

Carry allocation ID and selection revision through selector, attempt metadata, probes/model discovery, status writeback, cache projection and internal task data. Enforce per-allocation manual status and policy changes by ID. Scope credential service health explicitly: existing credential-and-model health observations can be shared by true equal credentials, but an asynchronous write verifies the selected ID, credential revision and model mapping before updating and cannot select the first matching index. Keep managed login/OAuth accounts unique per the existing provider refresh domain. A static Key can be repeated. When a provider exposes a stable managed account identity, route allocation references to its single refresh state and preserve account uniqueness. Provider modes without a safe reference contract reject private state cloning with a clear message.

## Shared accounts and reservations

| Record | Fields and guarantees |
| --- | --- |
| `channel_budget_accounts` | Unique `(scope_type, scope_id)`, scope `channel` or `key`. `enabled`, `limit_quota`, `period_used_quota`, `lifetime_used_quota`, `reserved_quota`, `reset_epoch`, `config_version` and `accounting_started_at`. Optional merge target and epoch mapping for retired entries. |
| `channel_budget_reservations` | Stable ID with unique opaque attempt key, channel/entry IDs, phase, task link, owner/expiry metadata for crash recovery, current settled amount and monotonic settlement revision. No credential, raw request or token. |
| `channel_budget_reservation_items` | Unique `(reservation_id, account_id)`. Store held amount and per-account settlement epoch. Scope identity remains immutable even when the entry is retired. |

The account limit and amounts use integer station quota units. Use existing checked conversion and range handling. Use checked 64-bit arithmetic for accumulated counters and compute capacity by subtraction after nonnegative bounds checks. For new accounts, initialize counters at zero and store start time. `lifetime_used_quota` is net actual over the ledger's life after refunds and repricing. Unlimited accounts continue tracking. Do not import historical `Channel.UsedQuota`, which remains a separate statistic.

The shared store exposes the following operations. Signatures are design contracts. The implementation should use existing transaction and error conventions.

| Operation | Contract |
| --- | --- |
| `ReadChannelBudget(ctx, scope, id)` | Return scope, enabled, limit, period used, lifetime used, reserved, remaining, epoch, config version and accounting start time. Unlimited remaining is absent. |
| `SetChannelBudgetLimit(ctx, scope, id, expectedVersion, enabled, limitQuota)` | CAS configuration. Preserve used, reserved and epoch. Turning enforcement off leaves counters enabled. |
| `ResetChannelBudgetUsage(ctx, scope, id, expectedVersion, operationID)` | Zero period used, increment epoch and configuration version, preserve all live holds and lifetime use. Repeat operation ID returns the prior result. A stale version conflicts. |
| `ReserveChannelBudgets(ctx, attemptKey, selection, reserveQuota)` | Verify current channel/entry identity, admission permissions and limits, then atomically reserve both scopes. Idempotent for identical attempt key and payload. |
| `SettleChannelBudgets(ctx, reservationID, revision, totalActualQuota, final)` | Release held quota on initial settlement and record actual. A linked task can revise cumulative actual while open. Same revision and total is safe to replay. Stale revisions cannot replace newer state. |
| `RefundChannelBudgets(ctx, reservationID, revision)` | Release a pending attempt or set an open task's total to zero after a confirmed funding refund. Use the same revision discipline to prevent reversal of a newer settlement. |

Lock order is channel configuration, affected Key entries ordered by ID, channel account, Key accounts ordered by ID, then reservations and items. Skip locks for unrelated records without reordering the ones acquired. Use existing `lockForUpdate(tx)` for MySQL and PostgreSQL and a SQLite write transaction/CAS with bounded retry on contention. Never keep SQL locks open during network calls. If an operation needs task and budget rows, establish their lock order before wiring it into task finalization. DB revisions and unique constraints enforce consistency across nodes.

## Request and task lifecycle

1. Request billing preparation and user/token funding rules still follow the existing path. Compute the budget reservation from the validated station estimate before each actual upstream send, after current channel/Key revision, ownership, model and eligibility checks. A trusted user may skip wallet pre-consumption while the estimated budget hold still applies. Use revised estimates after adapters change the existing validated estimate and before they send upstream. Maintain one reservation per attempted send, including zero-cost requests and attempts via public pools.
2. Enabled capacity is `limit - period_used - reserved`, floored at zero. Require positive capacity and enough capacity for the estimate. Enabled limit zero or depleted capacity rejects new requests even with a zero estimate. Exhaustion is a candidate rejection. Try another eligible allocation/channel within existing retry and binding rules. Do not disable the credential or replay after an upstream response has committed.
3. When existing billing finalizes a charge, settle the selected attempt using the same safe actual amount. One station charge contributes once to channel usage and once to the selected allocation usage. The admission estimate can be low. Settle the full amount and block new reservations when it exhausts the account. Do not retroactively cancel a delivered result or alter pricing. Release a failed, uncharged attempt before switching to another allocation. A fee attributable only to request policy stays in its current user billing path and does not become fake upstream Key consumption.
4. At asynchronous submission, link the reservation and allocation ID to durable `Task.PrivateData` and record submission-stage billable use according to existing task accounting. Later successful repricing sets a cumulative total, and successful funding refunds reduce that total to zero. Use the persisted task identity and settlement revision, never reroute accounting through current Key order. Keep task adjustments open until the terminal billing state is durable. Existing polling/retrieval of an accepted task continues after quota exhaustion. A follow-up operation that submits new paid upstream work is a new attempt.
5. Hook the ordinary HTTP paths, free and Playground flows, Responses WebSocket turns, Realtime, and built-in or plugin task submission through their existing admission/settlement boundaries. A turn with an estimate reserves it individually. A long-lived upstream session without a separate per-turn send boundary needs an admission check before it opens, records actual charge events and stops permitting new work when the next enforceable boundary exhausts capacity. Verify the boundary exists for each transport before claiming support. Admin probes/model discovery stay outside user settlement and attempt accounting.
6. Keep new ledger operations durable and independently retryable. Do not retry wallet/token adjustments just because budget persistence failed. Persist desired settlement and a revision in the existing durable task path or budget recovery state before acknowledging the transition. If ledger finalization fails, retain the hold, retry with the same operation identity and log a request/attempt-correlated reconciliation record. A definitely unforwarded attempt can expire safely. An ambiguous abandoned forwarded attempt cannot silently refund or disappear. Use a bounded reconciliation workflow that distinguishes a recoverable linked task, confirmed failure, and unknown terminal state requiring recorded administrative reconciliation. Prove recovery on process restart and prevent late callbacks from reviving a released reservation. No expiry may grant budget access while accepted work is still live.

Every active attempt adds a primary DB transaction, and settlement can add another. A failed authoritative read or reservation returns a retryable service error even on unlimited scopes. This makes enabling a limit on live accounts race-safe. Measure the additional primary DB round trips in a remote gateway before rollout and document the impact. Reuse the existing routing/admission milestones to avoid redundant DB trips. The account counters are not approximated through local Redis.

## Reset and deduplication

Limit edits preserve the current usage. Each scope resets independently. Increment the epoch, zero only that scope's period usage and preserve live reservations. A previously un-settled call finishing after reset contributes actual use to the new current period. A later refund or repricing of already settled work always updates lifetime use and changes period use only if that account item's settlement epoch still matches the account's current reset epoch.

Preview and apply deduplication within one channel under expected configuration revisions. Compare normalized credential identity, owner, model scope mode and normalized set, manual eligibility/status, enabled/limit and any additional effective restriction. Explicit allowlist and unrestricted scope differ even if currently equivalent. Skip a group with live reservations or a nonterminal linked task. Pick the smallest surviving active ID to stabilize apply across refreshes. Revalidate candidate revisions, state and account availability inside apply. If account updates since preview materially change shown totals, request a refreshed preview. Sum the current and lifetime counters of the merged accounts into the survivor and keep one configured limit. Show the recomputed remaining amount, including exhaustion.

Retire the merged entries and preserve history with a merge target on each retired account plus source and target epochs at the time of merge. Historical adjustments resolve that alias under the channel lock. Always adjust net lifetime use once at the surviving account. Forward the source settlement epoch to the target epoch only when it matched the source epoch at merge. Otherwise, or if the resulting epoch predates a subsequent reset, do not change current-period usage. Repeated merges compose this mapping and cannot make an old refund current. Keep immutable origin references in task history and reservation items. Existing channel totals remain unchanged by Key dedup. When a non-merge removal retires an allocation, historical adjustments stay on its retained account and the same channel account.

## Selection, model visibility and console

Retain the existing first-attempt bound user priority in `service/channel_select.go` and original billing group. Evaluate public-group eligibility and bound-user eligibility independently. Apply channel model, Key model scope, token model restrictions, status and exhausted-account filtering when building `/v1/models` and `/api/user/models`. Model listing can determine already exhausted budgets but cannot promise an unknown future request estimate will fit. Use grouped reads and cache invalidation for configuration, and recheck quota and ownership authoritatively before dispatch. Remote caches that are stale cannot authorize an invalid allocation. Keep the existing response shapes and do not disclose the bound credential or other users' permissions.

Extend the existing multi-Key table, edit flow and confirmations. Show owner/public, model scope, limit, current used and remaining. Keep reset separate from editing. Dedup preview shows masked rows, survivor, projected usage and skipped in-flight rows. Use existing monetary formatters and shared dialog controls. A stale action reloads and asks the user to retry against the new revision. Use appropriate channel management capability for write APIs and verify server-side. Record actor/scope/action/revision without credential material. Coordinate redaction and stable ID provenance with the request diagnostics task.

## Migration and rollout

Deploy compatible code and schema on all serving nodes, including pollers and Watchtower-managed instances, before activating allocation writes and budget enforcement. Backfill original rows idempotently with a shared DB rollout marker. Pause admission for the cutover and let old synchronous work drain. Old task records lacking the budget link finish through legacy billing and do not enter the new counters. Show the accounting start time. Enable duplicate/quota actions only after activation. Disallow mixed-version allocation writes or enforcement. After activation, use a compatible corrective release for rollback. Returning to a pre-allocation binary requires a coordinated recovery from a reviewed backup and cannot safely retain new permissions and enforcement simply from the old projection.
