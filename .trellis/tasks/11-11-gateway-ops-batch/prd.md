需求来自站点运营者（项目所有者）本人。下面每条先写「要什么」，再写「已定的口径」。口径里标了 **[假设]** 的是调度者替用户做的决定，实现时照做，并在报告里原样列出，方便用户事后推翻。

## R1 渠道粘性太死板，失败后不换渠道

现象：请求优先走会话粘性渠道；该渠道持续报错时，面板里设置的重试次数不起作用，不会换渠道，同一会话一直打到坏渠道上，直到客户端断开。面板「请求策略 › 会话默认设置（规则可继承或单独覆盖）」改了也没用。

已查明的原因（代码为准，行号可能有出入）：

1. 内置的两条会话规则（`codex cli trace`、`claude cli trace`，`setting/operation_setting/channel_affinity_setting.go`）带旧字段 `skip_retry_on_failure: true` 且没有 `session_mode`。`service/request_policy.go` 的 `EffectiveSessionMode` 把这种规则算成 `strict`，只有 `session_mode: "inherit"` 的规则才跟随全局默认。于是 `service/relay_error.go` 的 `DecideRelayRetry` 第一次失败就以 `strict_session` 停止，重试次数形同虚设，全局「会话默认设置」对这两条规则无效。
2. 粘性绑定只在渠道被禁用 / 不可用时清除（`service/channel_select.go` 的 `SelectChannelForRequest`），只在成功后改写（`RecordChannelAffinity`）。失败后绑定原样保留，客户端自己重发的下一个请求又回到同一个坏渠道，直到 TTL（默认 3600 秒）到期或渠道被自动禁用。
3. 即便进入重试，`model.GetRandomSatisfiedChannel` 按「第 N 次重试取第 N 档优先级」加权随机，不排除本次请求已经失败过的渠道，同档渠道可能再次抽中同一个。

要做的：

- 粘性仍然优先，但失败后能自动换渠道，并且后续请求不再回到坏渠道。
- 新增设置项全部放进「系统设置 › 请求策略」页，带说明文字，默认值按「更灵活」取：
  - **重试时避开已失败渠道**（开关，默认开）：同一请求内，重试优先选还没试过的渠道，先同优先级、再降级；全部试过后才允许重复。
  - **绑定渠道连续失败 N 次后解绑**（整数，默认 1，0 = 永不，即旧行为）：对所有会话模式生效。达到阈值时清除绑定；`strict` 模式下达到阈值的那次请求允许继续按重试次数换渠道，而不是直接停止。成功后按现有 `switch_on_success` 重新绑定。
  - 内置两条规则默认改为 `session_mode: "inherit"`；规则表里显示每条规则的「实际生效模式」，旧规则（空 `session_mode` + `skip_retry_on_failure`）要明确标出它是严格模式，并提供一键「全部改为继承默认」。
- 日志详情里的请求策略决策记录要能看出「解绑」「避开已失败渠道」这两类新决策。
- 普通转发、任务提交（`executeTaskSubmissionWith` / `decideTaskRetry`）、Responses WebSocket 三条路径口径一致。
- 指定渠道（pinned channel）、不可重试错误、流已开始输出等既有的停止条件不变。

验收：
- AC1.1 粘性渠道返回可重试错误时，同一请求在重试次数内换到其它可用渠道并成功；下一次同会话请求不再打到失败渠道。
- AC1.2 `strict` 规则在阈值为 0 时保持旧行为；阈值为 N 时第 N 次连续失败后解绑并换渠道。
- AC1.3 同优先级有 A、B 两个渠道、A 失败时，重试必定选 B（开关开）。
- AC1.4 新设置能在请求策略页保存、回显、校验非法值；旧配置不需要迁移就能启动。

## R2 速率限制：选分组 + 按用户覆盖

- 分组速率限制里，分组名改成从现有分组里选，不再手输；已存在但分组已被删除的旧条目仍能显示和删除。
- 用户默认遵循所在分组的速率；管理员可以在用户编辑里单独给某个用户设速率（总次数 / 成功次数，时间窗沿用全局）。
- 调整某个分组的速率时，对该分组全部用户生效、不影响其它分组；并提供「同时覆盖该分组内已手动设置的用户」的选项（勾选则清掉这些用户的单独设置）。
- 口径：用户级覆盖优先于分组设置；清除覆盖即回到分组。**[假设]** 用户级覆盖存成一个系统选项（用户 ID → `[总次数, 成功次数]`），不改表结构；实现者确认有更合适的落点可以换，但要说明理由。

验收：AC2.1 分组下拉列出现有分组；AC2.2 设了用户覆盖后该用户按覆盖值限流、同组其他人不变；AC2.3 「覆盖已手动设置的用户」只清目标分组内的用户；AC2.4 Redis 与内存两条限流路径都生效。

## R3 登录不强制二步验证 / Passkey

- 现状：用户（含管理员）只要录入了 TOTP 或 Passkey，登录就被强制二次验证（`securityVerificationPolicy` 的 `VerificationScopeLogin`）。
- 要做的：登录时的二次验证改为可选，默认不要求；其它高危操作的安全验证保持不变。
- 口径：
  - 每个用户在个人安全设置里有一个「登录时需要二次验证」开关，默认关。只有已录入 TOTP 或 Passkey 才能开。
  - 系统设置里加一个全站策略：`用户自选`（默认）/ `已录入者一律要求`（即旧行为）。
  - 关闭个人开关属于降低账号安全等级，必须先通过一次安全验证；开启不需要。
  - Passkey 作为无密码第一因子直接登录的流程不受影响。
  - 必须遵守 `AGENTS.md` 的「Authentication Security (OWASP Mandatory)」，在报告里写清引用的 ASVS 条目、做过的验证和遗留缺口。

验收：AC3.1 录入了因子但开关关的用户，密码 / OAuth 登录不再出现验证步骤；AC3.2 开关开或全站策略为「一律要求」时行为同现在；AC3.3 高危操作验证路径的既有测试全部照常通过；AC3.4 关闭开关必须带有效的安全验证证明，否则服务端拒绝。

## R4 登录网关头像

- 网关项目 `D:\MyNewWebProjects\azurekiln-oauth2` 的 userinfo / ID Token 已经带 `picture`（`server.js` 约 1183、1803 行），new-api 目前没有取这个字段。
- 要做的：OAuth / OIDC 登录时取头像地址并保存，每次登录刷新；前端凡是显示当前用户头像的地方（右上角用户菜单、个人资料页头部、移动端抽屉等）有地址就显示图片，没有地址或图片加载失败就显示现在的默认头像（首字母色块）。不允许出现空白。
- 口径：只接受 `https` 绝对地址（长度有上限），图片请求不带 Referer；用户不能通过个人设置接口自己改这个地址。**[假设]** 尽量不改表结构（例如放进用户 `setting` JSON）；确实需要加列时按 `AGENTS.md` 的数据库验证要求办。
- 只读网关项目，不改它；如果发现网关侧有缺口，写进报告。

验收：AC4.1 通过网关登录后用户菜单与资料页显示网关头像；AC4.2 地址为空 / 非法 / 加载失败时显示默认头像；AC4.3 自定义 OAuth 提供方与 OIDC 两条路径都覆盖。

## R5 排行榜缓存用量显示太丑

现状是这样的：

```
8.24B Token
↓66.9%
缓存读取
    30.2亿
缓存写入
    0
```

问题：总量是 `8.24B`、缓存是 `30.2亿`，单位风格不一致；标签和数值断行；整体挤成一列。

要做的：重排成看着舒服、与页面其它数字风格一致的样式。口径：与总量用同一套数字格式；标签和数值不换行分离；缓存读 / 写同一行或同一组；两者都为 0 时不显示；三处使用点（`market-share-section`、`model-leaderboard`、`models-section`）一起改，窄屏不溢出。

## R6 通用日志加「缓存命中率」小卡片

通用日志页头部现有「用量 / RPM / TPM」三个小卡片（`common-logs-stats.tsx` 的 `StatBadge`）。在 TPM 右边加一个风格完全一致的「缓存命中率」卡片。

口径：命中率 = 缓存读取 token ÷ 输入 token 总量（含缓存读取与缓存写入；注意 Anthropic 语义的 prompt 不含缓存、OpenAI 语义已包含，按结算语义换算，不能按模型名猜），统计范围与「用量」卡片一致（跟随当前筛选和时间范围），没有数据时显示 `-`。管理员视图与用户自己的视图都要有。

## R7 通用日志筛选支持模糊匹配

筛选项现在基本是完全匹配。要支持模糊（包含）匹配，并在筛选旁边提供一个切换。口径：**[假设]** 默认模糊，切到「精确」后恢复现在的行为；切换状态进 URL 参数；对文本类筛选（模型名、令牌名、用户名、分组、请求 ID 等）生效，数字 / 枚举类不变；统计卡片与列表用同一套筛选语义；`LIKE` 要转义通配符；ClickHouse 日志库分支同样支持。

## R8 分组等级

想要 `default < vip < svip < ultra < ultramax` 这样的等级：`default` 只能看到自己，`vip` 能看到 `default` 和 `vip`，以此类推；最高级能访问全部。现在只能逐个分组手工配可见性。

口径：分组多一个「等级」属性（整数，越大越高，未设置 = 不参与等级）。用户所在分组等级为 L 时，自动可用所有等级 ≤ L 的分组；与现有手工配置的可用分组取并集。所有读取「可用分组」的地方（令牌分组选择、模型广场 / 定价可见性、`auto` 分组、请求鉴权）统一生效，只在一处计算。在分组设置界面里可编辑等级，并能预览「这个分组能看到哪些分组」。

验收：AC8.1 按上面五级配置后各级可见范围符合描述；AC8.2 未设等级的分组行为与现在完全一致；AC8.3 低等级用户不能通过令牌或请求参数用到高等级分组。

## R9 邀请码注册

- 新增邀请码管理，功能与现有兑换码对齐：批量生成、名称、有效期、状态（未用 / 已用 / 停用）、搜索、启停、删除、清理失效、导出 / 复制，记录使用者与使用时间。一个码只能用一次。
- 新增独立开关「邀请注册」，与现有「开放注册」并列。
- 页面行为：

| 开放注册 | 邀请注册 | 登录页注册按钮 | 注册页 | 能否创建新账号 |
|---|---|---|---|---|
| 关 | 关 | 不显示 | 不可注册 | 都不行 |
| 关 | 开 | 显示 | 邀请码框 + OAuth / SSO 按钮，**不显示**用户名密码框 | 仅 OAuth / SSO，且必须带有效邀请码 |
| 开 | 关 | 显示 | 现状 | 现状 |
| 开 | 开 | 显示 | 用户名密码框 + 邀请码框 + OAuth / SSO 按钮 | **[假设]** 任何方式都必须带有效邀请码 |

- 邀请码要跟着 OAuth 往返走（参考现有 `aff` 的做法：`oauthStateRequest.Aff` → 服务端 auth flow 载荷），不能放在可被篡改的前端状态里。已有账号登录永远不需要邀请码。
- 邀请码的校验与核销必须在服务端、与建号同一事务内完成，并发下一个码只能成功一次；失败不消耗。错误提示不泄露码是否存在以外的信息，接口要有限流。
- 涉及注册 / OAuth，同样受 OWASP 条款约束。

验收：AC9.1 表中四种组合的页面与服务端行为一致（服务端强制，不靠前端隐藏）；AC9.2 同一邀请码并发注册只成功一个；AC9.3 邀请注册开、开放注册关时，密码注册接口被拒绝；AC9.4 管理页功能与兑换码页对齐。
